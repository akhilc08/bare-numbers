## Q1. Tool-calling benchmarks and error taxonomies: does any of them treat unit, format or convention errors in arguments as a category?

### Takeaway
None of the major tool-calling benchmarks (BFCL, API-Bank, ToolBench, tau/tau2-bench, NESTFUL, ToolSandbox, ACEBench, ToolScan, ComplexFuncBench, NoisyToolBench, ITC) has a "unit/currency/convention" error category. Unit and format mistakes are absorbed into a generic "parameter value error" bucket, and that bucket is consistently the largest or a dominant failure class (ACEBench; ComplexFuncBench: 78.8% of Qwen2.5-72B errors; tau-bench: about 55% of gpt-4o failures). The closest construct is ToolSandbox's "Canonicalization" category ("$" to "USD", "1B" to 1_000_000_000). There the unit or currency is explicit on the surface; in L4 it has to be inferred from culture. In BFCL's simple split, every unit-suffixed parameter matches the unit the user states (own analysis), so mismatch is never tested.

### Cited Findings
- **BFCL: Patil et al., "The Berkeley Function Calling Leaderboard (BFCL): From Tool Use to Agentic Evaluation of Large Language Models," ICML 2025 (PMLR v267)** — [PMLR](https://proceedings.mlr.press/v267/patil25a.html); [OpenReview](https://openreview.net/forum?id=2GmDdhBdDk); precursor Gorilla [arXiv:2305.15334](https://arxiv.org/abs/2305.15334) (Patil, Zhang, Wang, Gonzalez, 2023). BFCL grades calls by AST match of function name, parameters and types against a list of "possible answers" for each parameter. The V4 README adds a non-scoring "Format Sensitivity (5200)" category that varies prompt and return formats (Python, JSON, XML), not value conventions ([BFCL README](https://github.com/ShishirPatil/gorilla/tree/main/berkeley-function-call-leaderboard)). *Relation:* contrast and borrowable. *Positioning:* BFCL checks whether the value matches a string list, never whether it is in the right unit for the user.
  - **Own analysis of BFCL v4 `simple_python` (400 items, GitHub main, fetched 2026-10-07)** — [data](https://github.com/ShishirPatil/gorilla/tree/main/berkeley-function-call-leaderboard/bfcl_eval/data). 23/400 items (5.75%) expose a `unit`/`units`/`*_unit`/`currency`-type parameter, 25 parameters in total. Only 8 of the 25 are `required`, and 13 of the 25 accept the empty string as correct, so omitting the unit passes. Three items have unit-suffixed parameter names (`calculate_BMI(weight_kg, height_m)`, `calculate_cooking_time(weight_kg, temp_celsius)`, `calculate_carbon_footprint(daily_miles, …)`). In all three the user's query states the same unit as the suffix ("70kg and 1.75m", "1.5 kg", "20 miles"). *Relation:* supports (gap). *Positioning:* the most-used function-calling benchmark never puts a user-side unit that differs from the tool-side unit, which is the condition L4 isolates.
- **API-Bank: Li et al., EMNLP 2023** — [arXiv:2304.08244](https://arxiv.org/abs/2304.08244). 73 runnable APIs, 314 dialogues, 753 calls. Error distributions (Tables 4–5). Alpaca: No API Call 36.77%, False API Call Format 23.65%, API Hallucination 15.93%, Invalid Input Parameters 7.96%, Miss Input Parameters 1.17%. Lynx: API Hallucination 61.38%, Has Exception 16.40%, Invalid Input Parameters 8.47%, False API Call Format 6.88%, No API Call 5.29%, Miss Input Parameters 1.59% ([HTML §7.3](https://arxiv.org/html/2304.08244v2)). *Relation:* contrast. *Positioning:* "Invalid input parameters" is a format-validity class; a well-formed number in the wrong unit would count as correct.
- **ToolLLM/ToolBench: Qin et al., 2023** — [arXiv:2307.16789](https://arxiv.org/abs/2307.16789). 16,464 RapidAPI REST APIs across 49 categories, scored by an LLM-judged pass/win rate (ToolEval). ToolSandbox's related-work section criticises ToolEval for relying "solely on an LLM evaluator". *Relation:* contrast. *Positioning:* no argument-level taxonomy, so convention errors cannot be surfaced.
- **tau-bench: Yao, Shinn, Razavi, Narasimhan, 2024** — [arXiv:2406.12045](https://arxiv.org/abs/2406.12045). gpt-4o function-calling pass^1 is about 61% (retail) and about 35% (airline); pass^8 is under 25% (retail). The authors inspected 115 retail trajectories: 40 failed and 36 of those were agent failures. "Wrong argument or information provided" accounts for about 55% of failures and wrong decision-making for 25%. Hallucinated IDs per task: 0.46 for gpt-4o vs 2.08/6.34 for gpt-3.5 FC/Act ([HTML, Failure breakdown](https://arxiv.org/html/2406.12045v1)). The airline policy prices everything in "dollars" (e.g., "Each extra baggage is 50 dollars"). *Relation:* supports and borrowable (pass^k). *Positioning:* tau-bench's most common failure is the wrong-argument class, but its single-currency, single-locale domains cannot produce convention errors.
- **tau2-bench: Barres, Dong, Ray, Si, Narasimhan, 2025** — [arXiv:2506.07982](https://arxiv.org/abs/2506.07982). A dual-control telecom domain modelled as a Dec-POMDP, where both user and agent have tools. *Relation:* contrast (abstract only; I found no unit or locale dimension). *Positioning:* coordination between two controllers, but not across conventions.
- **NESTFUL: Basu et al., 2024** — [arXiv:2409.03797](https://arxiv.org/abs/2409.03797). 1,800+ executable nested call sequences. It includes "implicit API calling", where the query does not name the APIs needed, but the worked example is arithmetic, not unit conversion ([HTML](https://arxiv.org/html/2409.03797v3)). *Relation:* borrowable. *Positioning:* in NESTFUL the needed conversion is implied by the task; in L4 the need to convert is itself hidden.
- **ToolSandbox: Lu et al. (Apple), 2024** — [arXiv:2408.04682](https://arxiv.org/abs/2408.04682). 1,032 scenarios and 34 tools across 11 domains, including "Conversion". Canonicalization is defined as "transforming surface form representation commonly seen in a natural language query, to its corresponding canonical form… for example transforming 1B to 1_000_000_000, or $ to corresponding ISO 4217 currency code USD" ([HTML §3](https://arxiv.org/html/2408.04682v2)). Canonicalization (C) and Insufficient-Information (II) scores, read from the results table: GPT-4o C 76.6 / II 42.0; Claude-3-Opus 71.1 / 57.3; GPT-3.5-Turbo 70.4 / 22.3; Claude-3-Sonnet 65.5 / 44.2; Gemini-1.5-Pro 51.6 / 76.2; Mistral-7B 6.1 / 76.8; Gorilla-openfunctions-v2 8.9 / 69.2. A WebFetch summary had misread GPT-4o C as 84.0; that value belongs to the State-Dependency column. The paper notes that "time related arguments … show to be really challenging to canonicalize" and that models "take premature decisions in face of ambiguity". *Relation:* closest construct; low-to-medium novelty threat; contrast. *Positioning:* ToolSandbox tests canonicalization when the unit or currency marker is explicit ("$"), while L4 tests it when the marker is absent and only inferable from the user's culture.
- **ACEBench: Chen et al., 2025** — [arXiv:2501.12851](https://arxiv.org/abs/2501.12851). The error types for Normal data are param value error, output format error, param type error and function name error. "Param value error dominate across all models. This highlights the models' difficulty in generating specific values…" The "Special" split covers incomplete instructions, parameters that violate format or constraints, and irrelevant requests; most failures there are in *detecting* the problem ([HTML](https://arxiv.org/html/2501.12851v8)). *Relation:* supports. *Positioning:* L4 shows one specific, structured source of the dominant "value error" class.
- **ToolScan: Kokane et al. (Salesforce), 2024** — [arXiv:2411.13547](https://arxiv.org/abs/2411.13547). Seven error patterns: Insufficient API Calls, Incorrect Argument Value (IAV), Incorrect Argument Name, Incorrect Argument Type, Repeated API Calls, Incorrect Function Name, Invalid Format Error. IAC is the most prevalent ([HTML](https://arxiv.org/html/2411.13547v2)). *Relation:* borrowable taxonomy. *Positioning:* L4 can propose "convention error" as a sub-type of IAV.
- **ComplexFuncBench: Zhong et al., 2025** — [arXiv:2501.10132](https://arxiv.org/abs/2501.10132). 1,000 samples with multi-step constrained calls, "parameter value reasoning" and 128k context. "value_error accounts for a significant portion of errors in all models, particularly for Qwen2.5-72B, which has a value_error rate of 78.8%." stop_early rates are 19.7% for Claude-3.5-Sonnet and 21.0% for GPT-4o ([HTML](https://arxiv.org/html/2501.10132v1)). *Relation:* supports. *Positioning:* value errors dominate even without any cross-convention difficulty.
- **NoisyToolBench / Ask-when-Needed: Wang et al., EMNLP 2025** — [arXiv:2409.00557](https://arxiv.org/abs/2409.00557). Real user-instruction issues: Missing Key Information 56.0%, Errors 17.3%, Beyond Tool Capabilities 15.3%, Multiple References 11.3%. "LLMs tend to arbitrarily generate the missed argument" ([HTML](https://arxiv.org/html/2409.00557v4)). *Relation:* supports; AwN is a borrowable baseline. *Positioning:* a bare number is a missing-key-information case that does not look missing, because the tool's unit silently fills the gap.
- **HammerBench** — [arXiv:2412.16516](https://arxiv.org/abs/2412.16516) (Wang et al., 2024): imperfect instructions and argument shifts in mobile-assistant dialogues. **RelyToolBench** — [arXiv:2412.04141](https://arxiv.org/abs/2412.04141) (Xu et al., 2024): tool-selection vs tool-usage hallucination. **ToolBeHonest** — [arXiv:2406.20015](https://arxiv.org/abs/2406.20015) (Zhang et al., 2024): unsolvable-task diagnosis. *Relation:* contrast (I checked abstracts only and saw no unit dimension). *Positioning:* these are hallucination and imperfect-instruction benchmarks, not convention benchmarks.
- **International Tool Calling (ITC): Zhang & Zhu (Shenzhen Univ.)** — [arXiv:2603.05515](https://arxiv.org/abs/2603.05515). 3,571 real APIs, 17,540 tasks, 20 categories, 40 countries and 29 languages (English 69.48%), with 24 LLMs evaluated. Error types are tool selection (hallucinated, missing, extra) and invocation (incorrect, missing, extra parameters); the paper does **not** isolate currency, unit or date-format errors ([HTML](https://arxiv.org/html/2603.05515)). Caveat: the arXiv API gives v1 as 2026-01-21, which does not fit a 2603 identifier. *Relation:* low novelty threat; contrast. *Positioning:* it adds geographic diversity to the API pool, not to user conventions.
- **Programmatic tool calling: Patel et al., "The Bitter Lesson of Tool Calling," 2026** — [arXiv:2608.06370](https://arxiv.org/abs/2608.06370). Tools exposed as *typed Python stubs* match or beat native JSON tool calling in 11/14 models on BFCL v4. *Relation:* borrowable (typed quantity stubs). *Positioning:* typed interfaces are already practical, so a unit-typed stub is a realistic channel design.
- **Schema bias: Liu, Tan, Wang, Guo, "Action-Space Shaping for LLM Agents: Measuring and Mitigating Tool-Schema Bias," 2026** — [arXiv:2609.34971](https://arxiv.org/abs/2609.34971). Nine schema-rewrite operators (merge, split, renaming and others); "success rates range from complete failure to 97% depending solely on the schema". No operator changes where the unit is represented ([HTML](https://arxiv.org/html/2609.34971)). *Relation:* borrowable. *Positioning:* unit placement (in the name, in the description, as a typed field) is an untested schema transformation.
- **BiasBusters: Blankenstein et al., ICLR 2026** — [arXiv:2510.00307](https://arxiv.org/abs/2510.00307). "Semantic alignment between user queries and tool metadata is the strongest driver of selection; small perturbations to tool descriptions can significantly shift choices." *Relation:* supports (tool metadata steers behaviour). *Positioning:* L4's anchoring is the argument-filling counterpart of metadata-driven tool selection.
- **Tool documentation** — Hsieh et al. [arXiv:2308.00675](https://arxiv.org/abs/2308.00675) (zero-shot with documentation matches few-shot); EASYTOOL [arXiv:2401.06201](https://arxiv.org/abs/2401.06201) (concise unified tool instructions improve tool use); DRAFT [arXiv:2410.08197](https://arxiv.org/abs/2410.08197) (ICLR 2025 Oral; iterative documentation rewriting). *Relation:* borrowable (unit-in-description arm). *Positioning:* documentation quality is a known lever; L4 can test whether it moves conventions.

### Inferences
- The reviewer comment that "the unit is exposed in the tool parameter name" describes the *recommended* industry design (Google AIP-141, Q4), not an artifact. Every BFCL unit-suffixed parameter follows it, and none tests a mismatch. L4's anchoring therefore applies to well-designed APIs.
- Benchmarks score value correctness against the tool's own convention. Under that scoring, an mph=100 for an Iranian user is a *correct* call on any existing benchmark, which is why silent convention errors are invisible to current leaderboards.
- The closest scored category (ToolSandbox canonicalization) peaks at 76.6 for GPT-4o even with explicit markers. That suggests a ceiling below 100% even for the "unit known" control.

### Gaps
- ACEBench's per-model error percentages were not extracted (only the qualitative ranking).
- ToolSandbox's count of canonicalization scenarios was not confirmed (a WebFetch summary said 472 of 1,032; UNVERIFIED).
- tau2-bench, HammerBench, RelyToolBench and ToolBeHonest were checked at abstract level only.
- No benchmark reports a measured rate of unit or currency errors among argument errors. The only quantitative evidence is WorldBench's locale-mismatch share (Q3).

## Q2. Unit, quantity and numeral reasoning in LLMs, and conversion accuracy when the unit is known (NUMCoT and related; date and time-zone ambiguity)

### Takeaway
NUMCoT (Findings of ACL 2024) is the canonical "unit is known" conversion benchmark, but it tested 2023-era models. ChatGPT reached only about 46–80% on medium unit-conversion items depending on prompting, and CoT and injected conversion knowledge helped without closing the gap. More recent work shows that LLMs default to culturally dominant measurement systems (USD for fiscal values in 80% of cases on average) and are less accurate in non-default systems. Large-unit numeral translation ("million", "亿") still errs up to 20% for 8B models. There is no frontier-model (2026) conversion-accuracy number in the literature, so L4 must measure its own control.

### Cited Findings
- **NUMCoT: Xu, Tan, Wang, Yang, Xu, "NUMCoT: Numerals and Units of Measurement in Chain-of-Thought Reasoning using Large Language Models," Findings of ACL 2024, pp. 14268–14290** — [arXiv:2406.02864](https://arxiv.org/abs/2406.02864); [ACL Anthology 2024.findings-acl.848](https://aclanthology.org/2024.findings-acl.848/). The units dataset is a parallel Chinese/English set built on 18 common units (length, time, weight, money including yuan), with three splits. Easy: "856 grams = ? milligrams". Medium: "738 seconds − 5 milliseconds = ? milliseconds". Hard: "4 days 387 hours + 81 days = ? days ? hours". Models: ChatGPT, ERNIE-Bot-turbo, ChatGLM(-turbo/-6B), Llama-2 7B/13B/70B. Table 2, the units results on the Medium split, gives accuracy ZH/EN:
  - ChatGPT zero-shot: 45.50/48.00
  - ChatGPT zero-shot CoT: 68.83/77.33
  - ChatGPT few-shot CoT: 72.67/79.67
  - ChatGPT few-shot CoT with conversion knowledge: 73.67/76.00
  - Llama2-70B zero-shot: 18.67/44.33
  - Llama2-7B zero-shot: 7.83/18.50

  Accuracy falls as difficulty rises, and for units, unlike numeral conversion, CoT helps. On SUANJING (ancient Chinese arithmetic with unfamiliar units) ChatGPT is at 2.0–9.0% and Llama2-70B at 0%. Conclusion: "Despite the introduction of external knowledge and CoT, LLMs still struggle to effectively handle comprehensive problems involving numeral conversions and units of measurement" (from the PDF). Caveat: the Table 2 caption says "Numeral Conversions Medium split" although the table reports units; the caption looks like a typo. *Relation:* reviewer-requested control (borrowable); supports. *Positioning:* NUMCoT measures *conversion when the unit is given*; L4 measures whether the model *realises a conversion is needed*. The two failure sources should be reported separately.
- **Bui, Park, Glavaš, Schmidt, von der Wense, "On Generalization across Measurement Systems: LLMs Entail More Test-Time Compute for Underrepresented Cultures," ACL 2025 Main** — [arXiv:2506.02591](https://arxiv.org/abs/2506.02591). Seven open LLMs. Fiscal data defaults to USD in about 80% of cases on average (local currency about 17%). The default system gives the best performance in 28 of 35 model–dataset combinations, significant in 22. Llama 3.3 70B drops from 57% to 29% on the price-weight task when moved from the default "Kilogram" system to "Pound" (their accuracy-style metric). CoT mitigates the instability but raises test-time compute ([HTML](https://arxiv.org/html/2506.02591v1)). *Relation:* supports (defaults favour the dominant convention). *Positioning:* Bui et al. show the model's *output* convention prior; L4 shows the same prior acting on the *interpretation* of a user's bare input under tool pressure.
- **CAPRI: Miao, Zhu, Shwartz, "LLMs Infer Cultural Context but Fail to Apply It When Responding," 2026** — [arXiv:2606.17688](https://arxiv.org/abs/2606.17688). Models infer the user's culture and recall conventions (currency, distance, size, temperature) but often fail to adapt answers "unless explicitly prompted to perform the tasks sequentially". The task is VQA with no tool calls; the paper's only "tool" mention is an AI-usage statement ([HTML](https://arxiv.org/html/2606.17688v1)). *Relation:* L4's data source and main precedent (see Novelty threats). *Positioning:* L4 moves CAPRI's infer-vs-apply gap from answer generation to typed tool arguments and agent-to-agent messages.
- **Tang et al., "Investigating Numerical Translation with Large Language Models," ICASSP 2025** — [arXiv:2501.04927](https://arxiv.org/abs/2501.04927). A zh↔en numerical translation set from real business data with ten numeral types; "numerical types involving large units like 'million', 'billion', and '亿' … llama3.1 8b model can have error rates as high as 20%." *Relation:* supports (scale-word conventions such as Korean 만/억 are error-prone). *Positioning:* magnitude-word conventions are a sibling of unit conventions.
- **Kaye, "Analysis of Numerical Localisation in LLM Translations," 2026** — [arXiv:2608.05232](https://arxiv.org/abs/2608.05232). Five commodity-hardware LLMs localising times, numbers and dates; putting localisation principles into the prompt gave a statistically significant improvement. *Relation:* supports (prompt explicitness helps). *Positioning:* translation-side evidence that convention-awareness must be asked for.
- **Number Cookbook: Yang, Hu, Kang, Lin, Zhang, ICLR 2025** — [arXiv:2411.03766](https://arxiv.org/abs/2411.03766). A numerical understanding and processing benchmark: 4 representations × 17 tasks (41 combinations), with errors such as "9.11 > 9.9". **NumericBench: Li et al., ACL 2025** — [arXiv:2502.11075](https://arxiv.org/abs/2502.11075). Six basic numerical abilities, with persistent weaknesses in GPT-4 and DeepSeek. *Relation:* contrast. *Positioning:* L4's failure is not arithmetic; the number is passed through exactly.
- **MeasEval: Harper, Cox, Kohler, Scerri, Daniel Jr., Groth, SemEval-2021 Task 8, pp. 306–316** — [ACL Anthology 2021.semeval-1.38](https://aclanthology.org/2021.semeval-1.38/). Five subtasks: quantity span, *unit extraction* plus value modifier, measured entity/property, qualifier and relations; over 75 submissions from 25 participants. **CQE: Almasian, Kazakova, Göldner, Gertz, 2023** — [arXiv:2305.08853](https://arxiv.org/abs/2305.08853). A rule-based value+unit extractor with normalization (venue not verified; the arXiv comment gives only page counts). *Relation:* borrowable (quantity normalisation as a sender-side tool). *Positioning:* extraction work assumes the unit is written in the text; bare numbers are out of scope.
- **TAT-QA: Zhu et al., ACL 2021** — [arXiv:2105.07624](https://arxiv.org/abs/2105.07624). Hybrid table+text financial QA requiring numerical reasoning (TAGOP 58.0 F1 vs 90.8 for humans). That TAT-QA answers carry a "scale" label (thousand/million/percent) is from memory: UNVERIFIED, not in the abstract. *Relation:* borrowable if the scale label is confirmed. *Positioning:* scale (×10³/×10⁶) is a convention that silently changes magnitude, like units.
- **DateLogicQA: Bhatia, Tang, Mahanta, Kazi, 2024** — [arXiv:2412.13377](https://arxiv.org/abs/2412.13377). 190 questions over diverse date formats, introducing a Semantic Integrity Metric and showing Representation-Level and Logical-Level biases. **Date Fragments / DateAugBench: Bhatia, Peyrard, Zhao, 2025** — [arXiv:2505.16088](https://arxiv.org/abs/2505.16088). 6,500 examples, including "format-invariance puzzles"; "excessive fragmentation correlates with accuracy drops of up to 10 points on uncommon dates". *Relation:* supports (date-format conventions). *Positioning:* date-order ambiguity (DD/MM vs MM/DD) is the temporal analogue of bare-unit ambiguity.
- **GeoTemp: Holtermann, Röttger, Lauscher, "Around the World in 24 Hours: Probing LLM Knowledge of Time and Place," 2025** — [arXiv:2506.03984](https://arxiv.org/abs/2506.03984). 320k prompts covering 289 cities, 217 countries and 37 time zones, with 8 open chat models. Even the best model is "only 25.4% accurate on questions requiring both temporal and geographical knowledge" ([HTML](https://arxiv.org/html/2506.03984v1)). **Test of Time: Fatemi et al., 2024** — [arXiv:2406.09170](https://arxiv.org/abs/2406.09170). Synthetic temporal reasoning. *Relation:* supports (time zones are a locale convention models handle badly). *Positioning:* time-zone resolution is a further convention dimension L4 could add.
- **Imaging-101: Chen et al., 2026** — [arXiv:2607.10789](https://arxiv.org/abs/2607.10789). In 57 computational-imaging tasks, frontier coding agents show systematic problems with "physical convention handling". Per the search snippet, but not opened in full, this includes omitted unit conversions between sensor measurements and algorithm inputs. *Relation:* supports (agentic setting). *Positioning:* implicit unit conventions also break coding agents.
- **Typed unit calculi** — Allen, "A Calculus for Units of Measure with Conversion," 2026, [arXiv:2609.38242](https://arxiv.org/abs/2609.38242). Λ_S with Lean 4 mechanisation, explicitly motivated by the Mars Climate Orbiter. Foster & Wolff, ISQ/SI in Isabelle/HOL, [arXiv:2302.07629](https://arxiv.org/abs/2302.07629). *Relation:* borrowable (type-checked quantities). *Positioning:* programming languages solve unit safety with types; agent channels currently do not.

### Inferences
- The reviewers' NUMCoT request splits into two sub-questions. (i) With the source unit stated, how often do 2026 models convert correctly *inside a tool call*? (ii) How much of the 0–5% is inference failure versus conversion failure? NUMCoT's 2023 numbers (ChatGPT medium 48–80% EN) cannot stand in for this; L4 needs an explicit-unit control with the same tools.
- Bui et al. give a mechanism for "anchoring": models already default to the dominant convention. A tool parameter named in that convention (mph, usd) reinforces the prior rather than signalling a conversion.

### Gaps
- I found no benchmark of unit conversion *in function-calling form*: a tool in unit A, a user value in unit B, with conversion accuracy reported.
- Dedicated "dimensional analysis" LLM benchmarks: only physics benchmarks that list unit or dimensional errors as an error category turned up (UGPhysics [arXiv:2502.00334], CMPhysBench [arXiv:2508.18124]), from search snippets; not opened or verified.
- No QuantityQA dataset was found under that name.

## Q3. Locale-dependent number formats (decimal comma, thousands separators) and LLM agents

### Takeaway
The strongest quantitative evidence is WorldBench (2026). In 400 manually inspected failed agent trajectories, "locale mismatch" (wrong date order, decimal point vs comma) accounts for 6.8% of failures in English settings, 21.4% in non-English settings and 26.9% in Chinese. The authors call it "a grounding failure, since the agents parse the instruction correctly and then emit values under the conventions of the wrong locale." Medication-safety guidance (ISMP) flags the comma convention itself as locale-dependent.

### Cited Findings
- **WorldBench: Ranaldi, Shen, Kai, Birch, 2026** — [arXiv:2609.01056](https://arxiv.org/abs/2609.01056). 1,600 persona-grounded tasks in 7 languages and 8 cultures; the best agent reaches 49.2% Constrained Task Success. Appendix J (Table 10) shares of failures: Locale mismatch 15.2% overall, 6.8% EN, 21.4% non-EN, 26.9% Chinese. Localisation mismatch "occurs when the agent writes values in the conventions of the wrong setting, such as an American date order in an Italian task or a decimal point where a decimal comma is expected". In a French example, an agent that emits 42.56 fails the check "even when the underlying arithmetic is correct" ([HTML App. J, Fig. 14](https://arxiv.org/html/2609.01056v1)). *Relation:* supports strongly; medium novelty threat (see below). *Positioning:* WorldBench measures single agents *formatting outputs* in an explicitly declared locale; L4 measures agents *interpreting a bare input* whose convention is implicit, and how a second agent decodes it.
- **ISMP List of Error-Prone Abbreviations, Symbols, and Dose Designations (2024)** — [ISMP PDF](https://www.ismp.org/system/files/resources/2024-04/ISMP_ErrorProneAbbreviation_List.pdf). "Large doses without properly placed commas (e.g., 100000 units…) 100000 has been mistaken as 10,000 or 1,000,000", with the note: "Use commas to separate digits only in the United States; commas are used in place of decimal points in some other countries." *Relation:* supports (motivation). *Positioning:* safety-critical practice already treats digit grouping as a locale convention.
- **Ziemann, Eren, El-Osta, "Gene name errors are widespread in the scientific literature," Genome Biology 17:177 (2016)** — [doi:10.1186/s13059-016-1044-7](https://doi.org/10.1186/s13059-016-1044-7) (verified via Europe PMC, PMID 27552985). "Microsoft Excel, when used with default settings, is known to convert gene names to dates and floating-point numbers… approximately one-fifth of papers with supplementary Excel gene lists contain erroneous gene name conversions." *Relation:* supports (an analogue of silent receiver-side reinterpretation). *Positioning:* this is the classic case of a receiver decoding a bare string under its own default convention without any error signal.

### Inferences
- WorldBench's English vs non-English gap (6.8 vs 21.4) is the output-side mirror of L4's US-default anchoring. Citing both supports a general "Anglo-default convention prior" in agents.
- L4 currently varies units and currency. Adding decimal-comma and grouping-dot variants ("300.000" for a German user) would test whether a receiver misparses a sender's correctly converted number. This is a channel-format failure, distinct from unit inference.

### Gaps
- I found no peer-reviewed paper that specifically measures LLMs misreading decimal-comma CSVs or tables. The evidence found is practitioner GitHub issues from search snippets (not opened): eGEOagents issue #62 ("8,7 → 87"); llm4s issue #1515 (calculator tool formats with the JVM default locale); dataprof issue #433. These are anecdotal and should not be cited as findings.
- The CLDR number-symbol data (decimal and grouping separators per locale) in UTS #35 Part 3 was identified but its contents were not opened.

## Q4. Standards and API design for quantities: which ones require a unit or currency next to the value?

### Takeaway
Domain standards for data exchange carry the unit or currency *next to* the value: google.type.Money, Stripe PaymentIntents, schema.org QuantitativeValue and MonetaryAmount, UCUM and QUDT. The general-purpose agent interfaces do not. OpenAPI 3.1, JSON Schema 2020-12, MCP tool definitions and the A2A specification have no unit, currency or locale construct, so a tool argument's unit lives only in its name or description. Google's API guide (AIP-141) *requires* encoding the unit in the field name (`distance_km`), which is exactly L4's `mph` / `max_usd` design. BCP 47 with Unicode extensions already offers a standard way to state a principal's measurement system (`-u-ms-`), unit override (`-u-mu-`), currency (`-u-cu-`) and region (`-u-rg-`).

### Cited Findings
- **ISO 4217 currency codes** — the maintenance-agency secretariat is SIX ([SIX](https://www.six-group.com/en/products-services/financial-information/data-standards.html)). The official list, published 2026-09-17 ([list-one.xml](https://www.six-group.com/dam/download/financial-information/data-center/iso-currrency/lists/list-one.xml)), gives minor-unit digits: KRW 410 → 0; JPY 392 → 0; USD 840 → 2; EUR 978 → 2; IRR 364 → 2; BHD 048 → 3. The iso.org page blocked automated fetch. *Relation:* borrowable (currency_code field; minor-unit semantics). *Positioning:* the same integer means a different amount per currency (300000 minor units is ₩300,000 but $3,000.00), so an amount is uninterpretable without its code.
- **Stripe API** — [PaymentIntents create](https://docs.stripe.com/api/payment_intents/create): `amount` (Required) is "a positive integer representing how much to charge in the smallest currency unit (e.g., 100 cents to charge $1.00 or 100 to charge ¥100, a zero-decimal currency)". `currency` (Required) is a "three-letter ISO currency code, in lowercase". [Currencies](https://docs.stripe.com/currencies): zero-decimal currencies include JPY and KRW ("to charge 500 JPY, provide an amount value of 500"). Special cases: ISK must be sent two-decimal ("to charge 5 ISK, provide an amount value of 500"), and HUF payouts are treated as zero-decimal. *Relation:* borrowable (a mandatory currency next to amount; an L4 "Stripe-style" schema arm). *Positioning:* production payment APIs never accept a bare amount.
- **google.type.Money** — [money.proto](https://github.com/googleapis/googleapis/blob/master/google/type/money.proto): `currency_code` ("three-letter currency code defined in ISO 4217"), `units` (int64 whole units), `nanos` (int32, 10⁻⁹ units, sign-consistent; e.g., $-1.75 = units −1, nanos −750,000,000). *Relation:* borrowable. *Positioning:* this is a ready-made typed-quantity schema for the price concept.
- **Google AIP-141 "Quantities"** — [google.aip.dev/141](https://google.aip.dev/141): "Quantities with a clear unit of measurement (such as bytes, miles, and so on) **must** include the unit of measurement as the suffix… (for example, distance_km rather than distance_kilometers)", with the example `int32 distance_miles`. **AIP-143 "Standardized codes"** — [google.aip.dev/143](https://google.aip.dev/143): currency "must use ISO-4217 currency codes… and the field must be called currency_code"; "for representing an amount of money… use google.type.Money"; regions must use CLDR region codes (`region_code`); languages must use BCP-47 (`language_code`). *Relation:* key rebuttal material. *Positioning:* L4's tools follow Google's mandated naming, so unit-in-the-name is best practice, and anchoring happens *despite* best practice.
- **schema.org** — [QuantitativeValue](https://schema.org/QuantitativeValue): `value` (recommended type Number), `unitCode` ("The unit of measurement given using the UN/CEFACT Common Code (3 characters) or a URL"), `unitText`. [MonetaryAmount](https://schema.org/MonetaryAmount): `value` and `currency` ("Use standard formats: ISO 4217 currency format, e.g. 'USD'"). Note that `unitCode` is a separate property, not mandatory in the schema. *Relation:* borrowable. *Positioning:* the web's structured-data vocabulary separates value from unit.
- **UCUM (Regenstrief)** — [ucum.org](https://ucum.org/); [specification](https://ucum.org/ucum): "The purpose is to facilitate unambiguous electronic communication of quantities together with their units. The focus is on electronic communication, as opposed to communication between humans." Created by Gunther Schadow and Clem McDonald in 1999. *Relation:* borrowable (unit vocabulary for a typed channel; machine-to-machine framing). *Positioning:* UCUM's stated purpose is L4's design goal for agent-to-agent channels.
- **QUDT** — [qudt.org](https://www.qudt.org/): "semantic specifications for units of measure, quantity kind, dimensions and data types", originally developed for NASA's NExIOM project at Ames; use cases include conversion between units. *Relation:* borrowable (quantity kind plus dimension checks). *Positioning:* a richer, ontology-level alternative to UCUM.
- **BCP 47 / RFC 5646** — [RFC 5646](https://www.rfc-editor.org/rfc/rfc5646) (Best Current Practice, 2009): language tags "to indicate the language used in an information object", with registered extensions. **Unicode UTS #35 (LDML) v48.2, 2026-03-03** — [tr35](https://www.unicode.org/reports/tr35/). The Unicode `-u-` extension keys include: `ms` measurement system ("metric"; "ussystem: … pints are 16oz"; "uksystem: … pints are 20oz"); `mu` measurement-unit override (`celsius`, `kelvin`, `fahrenhe`); `cu` currency ("ISO 4217 code, plus others in common use"); `rg` region override. "The determination of preferred units depends on the locale identifier: the keys ms, mu, rg, the base locale… and the user preferences." **CLDR unit preferences** — [tr35-info](https://www.unicode.org/reports/tr35/tr35-info.html): e.g., `<unitPreferences category="length" usage="road">` gives kilometer/meter for 001 (world), mile/foot for US, mile/yard for GB and `mile-scandinavian` for SE. It also documents conversions such as mile-per-gallon → liter-per-100-kilometer via reciprocals. *Relation:* borrowable (a standards-grounded "publish the inferred locale" protocol). *Positioning:* L4's best non-oracle protocol (sender infers the locale, receiver resolves it) can be implemented with existing standards: BCP 47 tag plus CLDR unitPreferenceData.
- **OpenAPI 3.1.0** — [spec](https://spec.openapis.org/oas/v3.1.0.html): defined formats are int32, int64, float, double and password. A full-text search found **zero** occurrences of "unit(s)", "currency" or "locale". **JSON Schema 2020-12 Validation** — [spec](https://json-schema.org/draft/2020-12/json-schema-validation): no unit, currency or locale keyword (the search hits only "occurrence" and "language"). *Relation:* supports (gap). *Positioning:* the schema languages underneath LLM function calling cannot express units except in free text.
- **MCP tools (spec 2025-06-18)** — [modelcontextprotocol.io](https://modelcontextprotocol.io/specification/2025-06-18/server/tools): tools declare `inputSchema` as JSON Schema (e.g., `get_weather(location)`), with no unit, currency or locale mention. **A2A specification (latest)** — [a2a-protocol.org](https://a2a-protocol.org/latest/specification/): "unit" appears only as "unit of work/content"; no locale, currency or measurement field (consistent with the draft's "A2A agent cards (no locale field)"). *Relation:* supports. *Positioning:* neither of today's agent-interoperability standards gives a slot for the convention L4 shows gets lost.

### Inferences
- Design argument for the paper. A well-designed agent channel would carry, for every quantity: `{value, unit (UCUM or CLDR unit id), [quantity_kind]}`; for money, `{currency_code (ISO 4217), units, nanos}` as in google.type.Money; and a principal-locale tag (BCP 47, optionally `-u-ms-`/`-u-mu-`/`-u-cu-`/`-u-rg-`) so the receiver can resolve bare inputs through CLDR preferences. The L4 "typed message with mandatory unit field" is a partial instance; the locale tag would be its standards-grounded complement.
- Naming the unit in the parameter (AIP-141) informs the *receiver* but gives the *sender* nothing to hold onto. Typed {value, unit} fields force the sender to state a unit, but they can be filled with the tool's default, which is the anchoring risk. That is consistent with L4's typed message reaching about 62% rather than 100%.
- Minor-unit semantics (KRW 0, USD 2, BHD 3) show why the "bare number" problem compounds for currency: even with the correct currency, the scale convention must travel with the value.

### Gaps
- Whether OpenAI or Anthropic function-calling docs give any guidance on units was not checked.
- Whether the UN/CEFACT Rec. 20 code list is current was not checked.

## Q5. Real-world unit, currency and locale incidents usable as motivation (with verifiable sources)

### Takeaway
Four primary-sourced, high-profile cases map directly onto L4's mechanisms: Mars Climate Orbiter, Gimli Glider, Samsung Securities and paediatric dosing. Mars Climate Orbiter is a bare number crossing a team interface whose specification required units; the receiver assumed its own unit, and working-level concerns were "only informally reported". The Gimli Glider is a convention switch inside a pipeline of people, each assuming the other's unit. Samsung Securities is a Korean-won amount reinterpreted as a share count. Paediatric dosing errors double with non-standard units. Korean Air 6316 is the cleanest *relay* analogue: a first officer relayed "1,500 m" as "1,500 ft". It is supported here only by a secondary source. I found **no documented LLM-agent incident involving units or currency**.

### Cited Findings
- **Mars Climate Orbiter: NASA MCO Mishap Investigation Board, Phase I Report, 10 Nov 1999** — [NASA LLIS PDF](https://llis.nasa.gov/llis_lib/pdf/1009464main1_0641-mr.pdf).
  - Root cause: "the failure to use metric units in the coding of a ground software file, 'Small Forces,' used in trajectory models." The SM_FORCES output "was to be in metric units of Newton-seconds (N-s). Instead, the data was reported in English units of pound-seconds (lbf-s)."
  - "The SIS [Software Interface Specification], which was not followed, defines both the format and units of the AMD file."
  - Navigation "underestimated the effect on the spacecraft trajectory by a factor of 4.45 (1 pound force=4.45 Newtons)". The post-hoc periapsis estimate of 57 km was "too low for spacecraft survival", and the carrier signal was last seen on 23 Sept 1999.
  - "Concerns existed at the working level regarding discrepancies… but [were] only informally reported."

  *Relation:* supports (motivation). *Positioning:* a specification that mandates units is useless if the channel carries bare numbers and the receiver resolves them by its own convention, which is L4's sender-explicitness finding.
- **Gimli Glider: Lockwood, Final Report of the Board of Inquiry… Air Canada Boeing 767 C-GAUN… Gimli, Manitoba, 23 July 1983 (April 1985)** — [FAA-hosted PDF](https://www.faa.gov/sites/faa.gov/files/2023-10/Final%20Report%20of%20the%20Board%20of%20Inquiry.pdf).
  - Flight AC 143 from Montreal to Edmonton via Ottawa ran out of fuel over Red Lake, Ontario.
  - The factor supplied "was 1.77. This is the figure used to convert litres to pounds. The conversion factor to convert litres to kilograms is typically around .8."
  - 7,682 L × 1.77 = 13,597, which "was in pounds but everyone involved believed it to be kilograms"; the required fuel was 22,300 kg, and the computed amount to add, 8,703, was "assumed to be litres"-converted.
  - The report frames "the introduction of a so-called metric aircraft into a non-metric fleet" as a corporate cause.

  *Relation:* supports. *Positioning:* a multi-party pipeline where each step used a correct-looking number under the wrong unit, as in multi-hop agent relays.
- **Korean Air Cargo Flight 6316 (15 Apr 1999, MD-11F HL7373, Shanghai; 8 killed)** — [Wikipedia](https://en.wikipedia.org/wiki/Korean_Air_Cargo_Flight_6316): ATC cleared 1,500 m; the first officer "had confused 1,500 metres (4,900 ft), the required altitude, with 1,500 feet (460 m)". CAAC is cited as the investigating authority. The **primary CAAC report is UNVERIFIED** (not located online; aviation-safety.net returned 403). *Relation:* supports (relay analogue). *Positioning:* a human relay faithfully passed the number but substituted the receiver's unit. If used, cite cautiously as secondary.
- **Paediatric dosing: Yin et al., "Unit of Measurement Used and Parent Medication Dosing Errors," Pediatrics 134(2):e354–61 (2014)** — [doi:10.1542/peds.2014-0395](https://doi.org/10.1542/peds.2014-0395) (PMID 25022742; abstract via Europe PMC). In 287 parents across 2 emergency departments, 39.4% made an error measuring the intended dose and 41.1% the prescribed dose. Teaspoon/tablespoon units vs mL-only: 42.5% vs 27.6% errors (aOR 2.3, 95% CI 1.2–4.4) for the intended dose and 45.1% vs 31.4% (aOR 1.9, 1.03–3.5) for the prescribed dose. 16.7% used a non-standard instrument. "Findings support a milliliter-only standard." *Relation:* supports (a single mandated unit reduces errors). *Positioning:* medicine's fix is to standardise the unit on the channel, which is L4's typed-unit design.
- **ISMP 2024 error-prone list** — [PDF](https://www.ismp.org/system/files/resources/2024-04/ISMP_ErrorProneAbbreviation_List.pdf): "U" for units is "mistaken as zero or the number 4, causing a 10-fold overdose or greater"; "µg" is "mistaken as mg"; and for dram and minim symbols ISMP recommends "Use the metric system". *Relation:* supports. *Positioning:* error-prone unit notation is formally catalogued in safety-critical domains.
- **Samsung Securities "ghost shares" (6 Apr 2018)** — [Korea JoongAng Daily, 15 Jul 2018](https://www.koreajoongangdaily.com/business/debriefing-the-fatfinger-error/11845339). A dividend of 1,000 won per share was entered as 1,000 *shares* per share, creating 2.8 billion shares (89 million actually existed) with a theoretical value of 112 trillion won. 16 employees sold 5.01 million shares (182 billion won), the stock fell as much as 11.68% intraday, and the FSS sanctioned the firm. In August 2026 the Supreme Court upheld damages to the NPS ([Korea JoongAng Daily](https://www.koreajoongangdaily.com/business/samsung-securities-ordered-to-pay-19-billion-won-over-2018-ghost-stock-error/12820504); headline only, not opened). *Relation:* supports. *Positioning:* a Korean-won value read under the wrong unit (shares), the same won-denominated failure L4's Korean-budget example illustrates.
- **Mizuho Securities / J-Com (December 2005)** — [Al Jazeera, 9 Dec 2005](https://www.aljazeera.com/news/2005/12/9/224m-typo-shakes-tokyo-exchange). The firm "put in sell orders for 610,000 shares at one yen instead of one share at 610,000 yen" (more than 41 times J-Com's outstanding shares), losing at least ¥27 bn (about $224m). *Relation:* supports (field-role confusion between price and quantity). *Positioning:* a bare number entered into the wrong-typed slot.
- **Citigroup Global Markets (2 May 2022)** — [FCA press release, 22 May 2024](https://www.fca.org.uk/news/press-releases/fca-fines-cgml-27-million). A trader meant to sell a US$58m basket but created one worth US$444bn. Controls blocked US$255bn; US$1.4bn was sold across European exchanges. The fine was £27,766,200. A separate PRA penalty of £33.88m appears in search results but was not opened. *Relation:* contrast (a magnitude input error, not a convention). *Positioning:* use only as a "bare-number input" example if space allows.
- **LLM-agent unit or currency incidents: none verified.** A curated, CC BY 4.0 log of agent spending incidents ([Pink-Agentic-Payments/agent-spending-incidents](https://github.com/Pink-Agentic-Payments/agent-spending-incidents), 10 incidents, incidents.csv inspected) contains no unit or currency case. *Relation:* gap; it is also a framing opportunity ("before such incidents happen"). *Positioning:* L4 is preventive evidence, not post-mortem.

### Inferences
- The MCO report has three elements: (a) a specification required units, (b) the file carried bare numbers, and (c) the receiver assumed its own convention and discrepancies were noticed but not escalated. These map one-to-one onto L4's sender explicitness, bare-number channel and receiver silent-wrong vs ask. It is the best single motivating citation.
- Samsung (won vs shares) and Korean Air (m vs ft relayed by a human) pair naturally with L4's Korean and relay settings; flag Korean Air as secondary-sourced.

### Gaps
- Primary CAAC report for Korean Air 6316.
- An LLM-agent incident with units or currency. Practitioner GitHub issues about agent cost fields without a currency (AgentOps issue #1462, agentlens issue #366) surfaced only as search snippets and were not opened; they are not incidents.

## Novelty threats

### Takeaway
No paper found tests the core L4 condition: a tool or agent whose argument unit differs from the user's culturally implied unit, with the user's number bare. The closest are CAPRI (the same infer-vs-apply gap, in VQA answers), WorldBench (locale-mismatched *outputs* by agents), ToolSandbox canonicalization (explicit "$"→USD), and PTBench/UserToolBench (tool parameters inferred from a user profile). The draft already positions Finding 1 as a replication of CAPRI in a tool setting, which is the safe framing.

### Cited Findings
- **CAPRI** (Miao, Zhu, Shwartz 2026) — [arXiv:2606.17688](https://arxiv.org/abs/2606.17688). Threat: **medium** for Finding 1 (single agent; same data; same infer-vs-apply phenomenon). No tools and no agent-to-agent setting ([HTML](https://arxiv.org/html/2606.17688v1)). *Positioning:* L4 extends CAPRI from "answer in the user's unit" to "convert into the tool's unit / state the unit to another agent", and adds the silent-wrong vs ask outcome.
- **WorldBench** (Ranaldi et al. 2026) — [arXiv:2609.01056](https://arxiv.org/abs/2609.01056). Threat: **medium** for any claim that "agents ignore locale conventions" (locale mismatch is 21.4% of non-English failures). It does not cover bare-number interpretation, unit conversion into typed tools, or multi-agent channels. *Positioning:* WorldBench shows locale errors in agents' *outputs*; L4 locates where in a delegation chain the convention is lost and which channel design keeps it.
- **ToolSandbox canonicalization** (Lu et al. 2024) — [arXiv:2408.04682](https://arxiv.org/abs/2408.04682). Threat: **low–medium** (it already scores conversion of surface forms such as "$" into ISO codes). *Positioning:* explicit-marker canonicalization vs implicit-convention inference.
- **PTBench** (Huang et al. 2025) — [arXiv:2505.04072](https://arxiv.org/abs/2505.04072). "Profile-dependent Query": parameters missing from the query that must be inferred from the user profile. GPT-4-turbo parameter-value accuracy is 0.8123 for query-derived values vs 0.6832 for profile-derived values; overall 0.1847, against 0.2678 for their fine-tuned model ([HTML Table 2](https://arxiv.org/html/2505.04072v1)). **UserToolBench** (Yin et al. 2026) — [arXiv:2608.10042](https://arxiv.org/abs/2608.10042): latent preferences from interaction history (10 profiles, 36 tool sets, 1,065 turns, 170 tools), where "missing-constraint inference" is a major bottleneck. Threat: **low–medium**. *Positioning:* both infer *which value* from an explicit profile; L4 infers *which convention* a stated value is in from implicit cues. PTBench's query-vs-profile gap is a useful precedent.
- **On Generalization across Measurement Systems** (Bui et al., ACL 2025) — [arXiv:2506.02591](https://arxiv.org/abs/2506.02591). Threat: **low** (output defaults, no tools). *Positioning:* default-system prior as mechanism.
- **ITC** — [arXiv:2603.05515](https://arxiv.org/abs/2603.05515); **CASA** (NAACL 2025 Findings) — [arXiv:2410.23252](https://arxiv.org/abs/2410.23252), which tests web agents on cultural norms with <10% awareness coverage and >40% violation rates. Threat: **low** (no unit conventions). *Positioning:* geographic or cultural diversity without quantity semantics.
- **Schema bias** — [arXiv:2609.34971](https://arxiv.org/abs/2609.34971); **Faithful, Not Corrective** — [arXiv:2607.09678](https://arxiv.org/abs/2607.09678) (already cited in the draft; once an injected error is present, every format propagates it, with 83–100% surface persistence). Threat: **low** (interface and relay effects without conventions). *Positioning:* L4 adds the convention dimension to both literatures.

### Inferences
- The most likely reviewer objection is "this is CAPRI plus a tool". The defence is the channel-design results: the counterfactual sender-message replacement, the typed-unit field, and the confidence-gated hybrid. Finding 1 should stay framed as motivation.
- WorldBench (September 2026) is recent enough that reviewers may know it. Cite it as convergent evidence: locale errors are the growth term for non-English agent failures.

### Gaps
- Coverage: searches on arXiv, ACL Anthology and OpenReview, plus web searches for "tool call units locale", "implicit units function calling", "personalized tool invocation", "tool-schema parameter naming bias" and "cultural agents locale". Non-English venues and 2026 workshop papers were not searched.

## Experiment ideas borrowed from this literature (and implications for L4)

### Takeaway
The cheapest, highest-value additions answer the two reviewer points directly. (1) A NUMCoT-style conversion-accuracy control inside the same tool calls (the unit is stated, so only conversion is tested). (2) A unit-placement schema ablation, following the schema-bias paper's operator approach: name vs description vs typed field vs Money/Stripe objects. A standards-grounded locale-tag channel (BCP 47 + CLDR) and a number-format perturbation (WorldBench/ISMP) would strengthen the "what should the channel carry" argument.

### Cited Findings
- **E1. Conversion-accuracy control (from NUMCoT, [aclanthology 2024.findings-acl.848](https://aclanthology.org/2024.findings-acl.848/)).** Same items and tools, but the user states the unit explicitly ("100 km/h", "₩300,000"). Report correct / silent-wrong / ask, separating inference failure (bare-number condition) from conversion failure (explicit condition). Add NUMCoT-style Easy/Medium/Hard variants (single unit; mixed "1 h 20 min"; compound "km/h → mph"). For currency, supply a fixed rate in the tool description, so stale-rate errors cannot confound.
- **E2. Unit-placement schema ablation (operators in the style of [arXiv:2609.34971](https://arxiv.org/abs/2609.34971); naming rule from [AIP-141](https://google.aip.dev/141)).** The tool arms are:
  - (a) `speed_mph` (AIP-141 suffix; current design)
  - (b) neutral `speed` with "in miles per hour" only in the description (documentation lever; [arXiv:2308.00675](https://arxiv.org/abs/2308.00675))
  - (c) neutral name and no unit anywhere (does the model ask?)
  - (d) typed `{value, unit}` with a unit enum (schema.org [QuantitativeValue](https://schema.org/QuantitativeValue), [UCUM](https://ucum.org/ucum) codes)
  - (e) [google.type.Money](https://github.com/googleapis/googleapis/blob/master/google/type/money.proto) `{currency_code, units, nanos}`
  - (f) [Stripe](https://docs.stripe.com/currencies)-style minor-unit `amount` + required `currency`, which adds the KRW zero-decimal vs USD cents trap
  - (g) a unit-agnostic tool that converts server-side when given a unit

  Key metric: in arms (d)–(f), how often does the model fill the unit or currency field with the tool's example or default rather than the user's convention? That is anchoring that has moved into the typed field.
- **E3. Explicit-marker canonicalization contrast (from ToolSandbox, [arXiv:2408.04682](https://arxiv.org/abs/2408.04682)).** Inputs "$300,000" vs "300,000" vs "₩300,000" for the same Korean principal. This isolates the effect of the symbol from culture inference and lets L4 cite ToolSandbox's C scores as the explicit-marker reference point.
- **E4. Standards-grounded locale channel (from [UTS #35](https://www.unicode.org/reports/tr35/) / [RFC 5646](https://www.rfc-editor.org/rfc/rfc5646)).** The sender publishes its principal's inferred locale as a BCP 47 tag (e.g., `fa-IR`, `ko-KR-u-cu-krw`, `en-GB-u-ms-uksystem`). The receiver resolves bare quantities through CLDR unitPreferenceData (deterministic, outside the LLM) or through the LLM. Compare with the draft's "publish inferred locale" protocol and the oracle-locale bound. This turns L4's best protocol into a deployable standard recommendation and fills the gap noted in the A2A and MCP specs.
- **E5. Number-format perturbation (from WorldBench, [arXiv:2609.01056](https://arxiv.org/abs/2609.01056); [ISMP](https://www.ismp.org/system/files/resources/2024-04/ISMP_ErrorProneAbbreviation_List.pdf)).** Carry correctly converted values in locale formats ("1.500,5", "1,50,000" lakh, "30万") across the relay. Measure receiver misparsing separately from unit inference.
- **E6. Profile vs implicit cues (from PTBench, [arXiv:2505.04072](https://arxiv.org/abs/2505.04072)).** Add a structured user-profile field (`country: IR`) vs CAPRI's implicit-cue conversation. If the profile fixes anchoring, the failure is cue integration; if not, it is tool anchoring proper.
- **E7. Ask-when-Needed baseline (from NoisyToolBench, [arXiv:2409.00557](https://arxiv.org/abs/2409.00557)) and ToolSandbox's insufficient-information minefields.** Use AwN prompting as a named clarification baseline in place of, or alongside, the generic caution prompt. Score "ask" with the minefield logic: calling the tool with the wrong-unit value is the minefield.
- **E8. Reliability with pass^k (from tau-bench, [arXiv:2406.12045](https://arxiv.org/abs/2406.12045)).** Report silent-wrong^k: the probability that a channel design is never silently wrong in k trials. This suits safety framing and the MCO and Gimli motivation.
- **E9. Taxonomy contribution (from ToolScan, [arXiv:2411.13547](https://arxiv.org/abs/2411.13547), and ACEBench, [arXiv:2501.12851](https://arxiv.org/abs/2501.12851)).** Report L4 errors as a "convention error" sub-type of Incorrect Argument Value / param value error, with mutually exclusive subtypes: unit, currency, scale (minor units, 万/lakh) and number format. This makes L4 reusable by benchmark builders.
- **E10. Typed programmatic stubs (from [arXiv:2608.06370](https://arxiv.org/abs/2608.06370); type-theory framing from [arXiv:2609.38242](https://arxiv.org/abs/2609.38242)).** Expose the tool as a Python stub taking a `Quantity` (pint-style) that raises on dimensionless input. Does a hard type error turn silent-wrong into ask or convert?
- **E11. Format-restriction cost check (from "Let Me Speak Freely?", [arXiv:2408.02442](https://arxiv.org/abs/2408.02442): "stricter format constraints generally lead to greater performance degradation in reasoning tasks"; and JSONSchemaBench, [arXiv:2501.10868](https://arxiv.org/abs/2501.10868)).** Run the typed-message channel with and without constrained decoding. Constrained decoding guarantees a unit field is present but not that it is right, so report how often the field is valid but wrong.
- **E12. Relay unit-dropping injection (Korean Air 6316 analogue; complements [arXiv:2607.09678](https://arxiv.org/abs/2607.09678)).** Inject a relay hop that keeps the number but drops or rewrites the unit. Measure whether downstream receivers detect the problem when the principal's locale is available elsewhere in the context.

### Inferences
- **Implications for L4.**
  1. Add E1 and E2 before resubmission: they answer both reviewer comments and give a two-axis decomposition (inference vs conversion; where the unit lives).
  2. Use AIP-141 to reframe "unit in the parameter name" as a best practice the paper deliberately follows.
  3. Use the MCO report's "specification required units / file carried bare numbers / concerns informally reported" sequence as the opening motivation, with Samsung (₩ vs shares) as the currency case.
